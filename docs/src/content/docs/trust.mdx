PrismaLens puts a coding agent next to your code. This page says what that
agent can reach, what PrismaLens does to limit it, and where those limits stop.

## The short version

- The agent works in a **copy** of your repository, never in your checkout.
- PrismaLens **refuses** the agent's edits, deletes and known mutating commands. That is a guardrail, not a wall.
- The agent **cannot fetch URLs**. OpenCode also cannot web-search or read outside the snapshot.
- Runs are **not sandboxed**. Nothing at the operating-system level blocks a write or a network call; the report names the mechanism a run had.
- PrismaLens sends **no usage data** unless you opt in. An update check queries GitHub Releases without an identifier. Your agent sends your code and the alert to **its** model provider.
- PrismaLens **never** reads or stores your agent's login.
- Everything PrismaLens keeps is in **one folder**, `~/.prismalens`.

## The read-only policy

Coding agents ask their client before they act, and PrismaLens is that client.
It refuses edit, delete and move tools, and shell commands that look like
writes: redirects, `rm`, `mv`, `cp`, `chmod`, `sed -i`, state-changing git
commands, package installs, `docker`, mutating `kubectl`, `helm` and
`terraform` commands, `kill`, `wget`, and `curl` with `POST`, `PUT`, `PATCH` or
`DELETE`. Reading, searching and commands like `ls`, `grep` and `git log` are
allowed.

<Aside type="caution" title="This is a guardrail">
The shell rules match command text, so a command written to dodge them, such as
a short Python script that writes a file, gets through. The policy catches an
agent making a mistake. It does not stop an agent that was talked into
misbehaving by text it read. For a real boundary, run PrismaLens under a user
or in a VM that can read only what it should, and give the agent read-only
credentials for anything outside the copy.
</Aside>

PrismaLens refuses paths outside the snapshot, judged where they really land:
through `..`, symlinks, `~` and globs such as `cat *`. Like the rest of the
policy, it matches command text, so the agent can still read any file your user
can read if it writes a command that dodges the rules. Keep that in mind before
you run PrismaLens under an account that can read production credentials.

Agent configuration committed in the repository never reaches the agent:
before a run starts, PrismaLens removes `.claude`, `.opencode`, `opencode.json`,
`.mcp.json`, `.gemini` and `.codex` at any depth from the snapshot, so a
repository cannot bring its own tools, hooks or instructions into the run.

Alert fields reach the agent inside a block marked as untrusted data. If the
agent spots text trying to give it orders, it quotes it in the report under
**Content tried to instruct the agent**.

## What leaves your machine

- **From PrismaLens:** no analytics unless you opt in (see [Usage telemetry](#usage-telemetry)), and no crash reports. An update check queries GitHub Releases without an identifier. The app listens on `127.0.0.1` unless you pass `--host`.
- **Update check:** once a day `pl up` checks GitHub Releases for a newer version by sending a `HEAD` request to `https://github.com/prismalens/prismalens/releases/latest`. The check sends no identifier, query, or body — only the standard IP address and User-Agent header of any HTTP request. Results are cached for 24 hours in `update-check.json` in the workspace folder. The check runs in the background and never delays startup. It is suppressed when standard output is not a TTY, in CI, when running under an Electron launcher, or when `PRISMALENS_UPDATE_CHECK=off` or `DO_NOT_TRACK` is set.
- **At install:** a documentation dependency of the API contains an install-time analytics package (`@scarf/scarf`). Set `SCARF_ANALYTICS=false` before `npm install -g prismalens` to turn it off.
- **From your agent:** what it reads, including source code, command output and the alert, goes to its model provider, as it would if you used the agent directly.
- **From git:** fetching a repository URL contacts that host with your git credentials.

## Usage telemetry

Usage telemetry is **off by default**. Nothing is sent until the instance owner opts in.

### Where you answer

The question is asked once:

- **On `/incidents`:** Until you answer, a consent banner sits above the incidents list. It offers **No thanks** and **Share usage data**. Choosing either hides the banner.
- **In Settings:** Under **Settings → Usage data**, the **Share usage data** toggle lets you change your decision at any time.
- **`pl up --telemetry=off`:** The CLI flag disables usage telemetry for that run (`--telemetry` accepts only `off`; turning telemetry on must be done in Settings). While undecided, `pl up` prints a one-line notice pointing at Settings, but never prompts in the terminal.

### What forces it off

Three environment variables force telemetry off regardless of what is stored in Settings:

- `PRISMALENS_TELEMETRY=off` (also accepts `0` or `false`): Disables telemetry for the process.
- `DO_NOT_TRACK`: When set to any value other than empty, `0`, `false`, or `off`, disables telemetry (and the update check).
- `CI`: Any non-empty value disables telemetry. Automated runs cannot give consent and are never counted as installs.

When forced off, the Settings checkbox is disabled with a note explaining the environment override, and no events are collected or sent.

### The install id, and your consent

- **What it is:** A random UUID generated once for the workspace. It is sent as the `distinct_id` on every event so PrismaLens can count installs rather than disconnected events.
- **Pseudonymous data:** Because the identifier is stable per install, it is pseudonymous rather than anonymous, and is treated as personal data under GDPR Recital 26. Consent is the sole legal basis for collection. It is never joined to an account, email, or user profile.
- **Where it lives:** In the workspace SQLite database (`prismalens.db`) in the `settings` table under the `TELEMETRY` key. A factory reset deletes this row; a reset instance generates a fresh install ID and asks for consent again.
- **Retention:** Events are kept for as long as PostHog's plan retains them — at least one year on the plan we use — and are not joined to anything else.
- **Withdrawal:** To withdraw consent, uncheck **Share usage data** in **Settings → Usage data**. Collection stops immediately from that moment. You can also pass `pl up --telemetry=off` or set `PRISMALENS_TELEMETRY=off` or `DO_NOT_TRACK=1`.

### What is sent

- An install id: a random identifier created once for this workspace.
- The PrismaLens version, whether it is a release or a development build, how it was installed (npm, the installer, Homebrew, Scoop or the desktop app), the operating system, CPU architecture and Node major version.
- One event per milestone, carrying fixed categories only: setup finished; a service gained a repository (local folder or git); an integration was configured (which vendor); the first alert this install ever received (which source); an investigation started (which coding agent, and whether it was asked for by hand or by an alert); an investigation ended (its outcome, how long it took as one of four ranges, and a category for the failure); a report was viewed; a report was exported (Markdown, Slack or a GitHub comment); an incident was closed.
- Once a day while PrismaLens is running and sharing is on: a sign that this install is active, with nothing else attached.

To check this against what actually leaves your machine, open **Settings → Usage data → Recently sent**: the last 20 events exactly as sent, less the PostHog project key, kept in memory until PrismaLens restarts.

Events go to PostHog Cloud EU (Frankfurt).

### What is never sent

Every event property is an enum, a duration bucket, a bounded integer, or a boolean. The API runs all outbound properties through `sanitize()`, which drops any undeclared property or value outside the declared set before building a request.

PrismaLens never sends:

- **IP addresses or geolocation:** Every event carries `$geoip_disable: true` and `$process_person_profile: false`, and the PostHog project discards the client IP rather than storing it or resolving it to a location.
- **User identities:** No email addresses, names, or user account IDs (`posthog.identify` is never called).
- **Repository contents:** No source code, repository names, git remote URLs, branch names, commit hashes, or workspace file paths.
- **Alert content:** No alert text, payloads, labels, or annotations.
- **Time of day:** Each event is recorded with its date only, never the time of day: its `timestamp` is midnight UTC of the day it was sent.
- **Agent data:** No prompts, model outputs, agent thoughts, or credentials.
- **Error messages:** Investigation errors are classified into a fixed enum class (`error_class`) inside the service; the error message text is discarded and never sent.
- **Hostnames or machine identifiers:** No hostnames or machine names.

Every event sent when telemetry is enabled carries a common platform block, plus event-specific properties drawn from closed sets:

## Credentials

| Credential | What PrismaLens does |
| --- | --- |
| Your agent's login | Never reads, copies or stores it. |
| Provider keys in your environment, such as `ANTHROPIC_API_KEY` | Passes the keys the chosen agent reads into its environment. Never stores them. |
| A gateway for Claude Code | Set `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN`; the model you set in Settings applies to every tier. The URL must be `https://` unless it is on this machine. |
| Your git credentials | Never reads them. Git uses them. |
| A GitHub token you add in Settings | Stores it encrypted and sends it only with git requests to GitHub. |
| PrismaLens's own secrets | Generated on first start, stored as owner-only files, never given to the agent. |

Apart from those provider keys, the agent gets only `PATH`, `HOME`, `USER`,
`LOGNAME`, `SHELL`, `PWD`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TERM`, `TMPDIR` and
`TZ` from your environment.

There are no accounts. A browser gets in only by opening a one-time pairing
link that `pl up` or `pl pair` prints on the host; no address, `localhost`
included, grants access by itself. Only the host's own session can pair or
revoke other devices. See [Opening it from other devices](/guides/devices/).

## Where your data lives

Everything is under `~/.prismalens`, or the folder you pass to
`pl up --workspace`.

| Path | Contents |
| --- | --- |
| `prismalens.db` | Incidents, alerts, services, investigations, reports and their event streams |
| `runs/<id>/repo` | The snapshot a run read, deleted when the run ends, whatever its outcome |
| `runs/<id>/transcript.jsonl` | Raw messages between PrismaLens and the agent, kept as a best effort |
| `repos/` | Mirrors of repositories added by URL |
| `logs/` | App logs |
| `PRISMALENS_*_FILE` | Generated secrets |

To remove everything, stop `pl up` and delete the folder.

## These websites

prismalens.io and docs.prismalens.io count visits with PostHog Cloud EU, without
cookies or browser storage. They record which pages are opened and when a link to
npm, GitHub or a release is clicked, or an install command is copied. The landing
site also records where on the page people click, as a heatmap. Nothing typed
into a page is recorded, IP addresses are not stored, and a visit is never
linked to an install of PrismaLens.
