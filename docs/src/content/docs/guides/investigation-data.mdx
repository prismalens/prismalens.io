An investigation needs more than the code: the metrics around the alert, the
logs, the incidents that looked like this one. PrismaLens gives the agent one
doorway to all of it, a **gateway** that runs inside the app. The agent calls
named tools on it. It never gets a URL or a password for your Prometheus,
Alertmanager or Loki.

## What the agent can call

Every tool is read-only. Each query tool takes an optional `source`, an id or
label, for when more than one source of its kind is connected, and answers
`not-configured` when none is.

| Tool | What it returns | Cap |
| --- | --- | --- |
| `sources_list` | Metrics, logs, code, deploys and knowledge, each `connected`, `not-configured` or `unreachable` | Never carries upstream error text |
| `investigations_search` | Completed past runs matching `query`, optionally for one `service`. The agent's finding and the cause an operator recorded stay in separate fields | `limit` 1 to 20; never the calling run |
| `prometheus_query` | An instant query | 50 series, 200 points per series |
| `prometheus_query_range` | A range query; the step defaults to about 200 points | 50 series, 200 points per series |
| `prometheus_alerts` | The alerts Prometheus has firing | 100 alerts |
| `alertmanager_alerts` | Active alerts by default; takes matchers | 100 alerts |
| `loki_query_range` | Log lines across streams | `limit` 1 to 500 lines, each cut at 2,000 characters |

Every query tool also reads at most 4 MiB from the upstream and returns at most
32,000 characters. A source that cannot be reached comes back with a reason in
PrismaLens's own words, such as "answered HTTP 401" or "redirected to another
host", never the upstream's reply.

## How a call travels

```text
agent         ACP session      gateway (in PrismaLens)      Connection       upstream
  |                |                      |                      |               |
  | tools/call     |                      |                      |               |
  | prometheus_    |                      |                      |               |
  |   query        |                      |                      |               |
  |--------------->| POST /api/mcp/runs/<run>                    |               |
  |                |  Authorization: Bearer <this run's token>   |               |
  |                |--------------------->| check token and run  |               |
  |                |                      | find the source      |               |
  |                |                      |--------------------->| decrypt; bind |
  |                |                      |                      | to its origin |
  |                |                      |                      |-------------->|
  |                |                      |                      |<--------------|
  |                |                      | cap, scrub secrets   |               |
  |<---------------|<---------------------|                      |               |
  | trimmed result |                      |                      |               |
```

1. At the start of the run, PrismaLens offers the agent one MCP server named
   `prismalens` over ACP, with a bearer token that works for that run only.
2. The agent calls a tool. The gateway checks the token against the run in the
   URL. A token for another run, a revoked token and a missing token all get
   `401`.
3. The gateway finds the matching **Connection** (the source you saved under
   **Settings → Data sources**), and PrismaLens, not the agent, makes the
   request.
4. The reply is trimmed to the caps above, with every credential value
   removed, and goes back to the agent.

## What stays out of the agent's reach

- **Credentials stay in PrismaLens.** They are stored encrypted, and a
  credential is sent only to the origin of its source's own URL. A redirect to
  another host fails before anything is sent there.
- **Scrubbed on the way out.** Credential values, including the base64 form of
  basic auth, are removed from tool results and from upstream error bodies.
- **Read-only floor.** Every tool carries the read-only hint and the gateway
  offers no tool that writes. This does not depend on the run's
  [permission level](/coding-agents/#permission-levels-and-asks).
- **The token dies with the run.** It is held in memory, ends when the run
  ends, fails or is stopped, and a restart forgets every token.
- **Only the run's token opens it.** A paired device or a session never opens
  the gateway.

A source saved with a sign-in method PrismaLens cannot use yet is refused, and
a stored one makes its tools say `<name> credentials are not supported yet`.
The kinds are on [Connect a source](/guides/connect-a-source/#how-a-source-signs-in).

## Which agents take the tools

The gateway reaches an agent only if the agent says, at the ACP handshake, that
it takes HTTP MCP servers. Otherwise PrismaLens sends none, and the run's
conversation says "The agent does not take PrismaLens tools". Before the first
prompt, the transcript notes which happened.

| Agent | Takes PrismaLens tools |
| --- | --- |
| Claude Code | Yes, seen in a real run |
| OpenCode | Expected from its source; not yet seen in a run |
| Gemini CLI | Expected from its source; not yet seen in a run |
| Codex | Pending |
| deepagents | No |

An agent that does not take the tools still investigates, from the code and
from the credential-free Prometheus and Alertmanager addresses in its prompt.
A source that needs a credential is out of its reach.

## What it looks like

The calls from a Claude Code run, as the transcript names them:

```text
mcp__prismalens__sources_list
mcp__prismalens__prometheus_query
mcp__prismalens__prometheus_query_range
mcp__prismalens__prometheus_alerts
mcp__prismalens__investigations_search
mcp__prismalens__alertmanager_alerts      -> not-configured
```

The last call shows the floor: no Alertmanager was connected, so the tool said
so instead of guessing. Connect one on
[Connect a source](/guides/connect-a-source/).
