title: How investigations reach your data
description: What PrismaLens reads before a run starts, which connection and credential it picks for each source, what the report says it covered, and the read-only tools an agent gets during the run.
---

An investigation needs more than the code: the alerts and deploys around the
incident, the metrics and logs over its window, the runbooks, the incidents
that looked like this one. PrismaLens reads that **before the run starts** and
hands it to the agent as files and a few lines of the prompt. During the run,
the agent gets a handful of read-only PrismaLens tools; anything else it
queries, it queries with the tools your own agent setup gives it.

## The order of a run

```text
incident ─▶ PrismaLens, before the run
             1. the incident, its alerts, and deploy and change events   (from PrismaLens's database)
             2. the repository checkout                                  ┐ at the same time, each with its own deadline
                a telemetry snapshot: Prometheus, Alertmanager, Loki     ┘
                the runbooks in the bound repositories                     read once the checkout is done
             3. the snapshot is stored with the run and copied to
                .prismalens/runs/<run id>/ in the run's working directory
          ─▶ the agent, during the run
             reads the copies and the code; calls PrismaLens's read-only tools on a server named for this run;
             uses its own tools and its own MCP servers for anything else
          ─▶ the report, with what was read, what was empty and what was skipped
```

Nothing before the run can fail an investigation. A source that is down, slow,
missing its credential or over a limit is skipped, written to the run log, and
named in the report; the run starts without it.

## What PrismaLens reads before the run

| What | Where from | Limit |
| --- | --- | --- |
| The incident, its alerts, and deploy and change events for its services from a day before it started | PrismaLens's own database | Each read gives up after 10 seconds |
| The code at the commit the run reads | The service's repository; see [Services and their code](/guides/services/) | All checkouts share 10 minutes, at most 3 at a time; what is unfinished then is skipped |
| Prometheus: alerts firing and scrape targets down over the window | The connection picked for the service | 10 seconds per source, 15 seconds for the whole snapshot, at most 6 sources |
| Alertmanager: active alerts over the window | as above | as above, 100 alerts |
| Loki: error, exception, fatal and panic lines over the window | as above | as above, 200 lines, each cut at 2,000 characters |
| Runbooks | Markdown under `runbooks/` and `docs/runbooks/`, `RUNBOOK*.md`, and runbook links in `catalog-info.yaml`, in the bound repositories at the commit the run reads | 10 seconds; a link is listed, never fetched |
| Similar past incidents | PrismaLens's own database | |

The **window** runs from half an hour before the first alert to now, at most
six hours back and at least fifteen minutes. Loki is read with the selector set
on the service's mapping, or `{service_name="<service>"}` when there is none.
Each source's part of the snapshot is cut at 256 KiB, oldest log lines first.

## Which connection and credential a source uses

For each kind (Prometheus, Alertmanager, Loki), PrismaLens picks per service
of the incident: the incident's own service, then each alert's.

1. **A connection mapped to the service.** Map one in the service's
   **Connections** section; with several, higher rows win. A mapping can carry
   a **Deployment tag**. When the incident names a deployment, the mapping
   tagged with it wins; then an untagged one; then one with another tag. The
   deployment comes from the first alert label among
   `deployment_environment`, `deployment.environment.name`,
   `deployment.environment`, `environment` and `env`, and otherwise from the
   `environment` of the service's latest deploy event.
2. **The only connection of that kind**, when none is mapped to the service.
3. **The environment PrismaLens started in**: `PROMETHEUS_URL`,
   `ALERTMANAGER_URL` or `LOKI_URL`, with `PROMETHEUS_TOKEN`,
   `ALERTMANAGER_TOKEN` or `LOKI_TOKEN` when set.

With several connections of a kind, none mapped to the service and no
environment variable for it, that kind is skipped with `2 prometheus connections, none mapped to checkout: map one on
the service`. With nothing at all, the report says `No Prometheus is set up for
checkout.`

Inside a picked connection, a credential saved in PrismaLens wins over the
environment. A `PROMETHEUS_TOKEN` (and the others) fills in only for a
connection with no saved credential, and only when `PROMETHEUS_URL` has the
same origin as the connection. When a saved credential overrides one in the
environment, the report says which, for example **Over** `PROMETHEUS_TOKEN`.

Code is read with a token saved for the repository's host, then a token from the
environment, then this machine's own git login; see
[Git credentials](/guides/git-credentials/) for the order and where each is
shown.

### Worked example: prod and staging

The service `checkout` has two Prometheus connections mapped, `prom-prod`
tagged `prod` and `prom-staging` tagged `staging`. No Loki connection is
saved, and PrismaLens was started with `LOKI_URL` and `LOKI_TOKEN`. The only
Alertmanager connection, `am-prod`, is not mapped to any service, and it does
not answer. An alert arrives with the label `env="prod"`.

The run log, before the run:

```text
pre-run: read prom-prod (prometheus) (mapped to checkout, priority 2, deployment prod named by the alert): 3 alerts firing in the window, 1 scrape targets down in the window
pre-run: skipped am-prod (alertmanager, set) (the only alertmanager connection; not mapped to a service): the source did not answer in time
pre-run: read LOKI_URL (loki) (env LOKI_URL; no connection is mapped to checkout): 0 error log lines from 0 streams for {service_name="checkout"} (the default selector)
```

Had the alert said `env="staging"`, the first line would name `prom-staging`.
Had it named no deployment and the latest deploy event said
`"environment":"staging"`, the line would end `deployment staging named by the
latest deploy event`.

The report's coverage reads **2 read, 1 skipped**, one row per source:

| Source | Result | Credential |
| --- | --- | --- |
| prom-prod | Data found | Set in PrismaLens |
| am-prod | Skipped: the source did not answer in time | Set in PrismaLens |
| LOKI_URL | Nothing in the window | From environment |

## Coverage: what the report tells apart

| Result | Means |
| --- | --- |
| **Data found** | Queried, and the window had something. |
| **Nothing in the window** | Queried, and the source answered with nothing for the window. |
| **Skipped** | Not read, with the reason: did not answer in time, could not connect, the credential could not be used, or the request would leave the source's origin. |
| **Not read** | Past the 6-source limit; never tried. |

A kind with no source at all is listed under the coverage as not set up. A
runbook scan or a whole telemetry snapshot that misses its deadline is named
the same way.

## The snapshot folder

The snapshot is stored with the run, and a read copy goes into each working
directory the agent starts in. For the example above:

```text
.prismalens/runs/
  .gitignore                       *  (the copies never show in git status)
  cmh3x9k2p0001/
    index.json                     what was read, skipped and not set up, with the start of each source's data
    telemetry-prometheus-1.json    the source, the window and its data
    telemetry-loki-1.json
    past-incidents.json
    runbooks.md
```

The prompt names the folder and each file, and the agent reads them like any
other file:

```text
PRE-RUN CONTEXT
  PrismaLens read this before the run, at 2026-10-28T14:02:11.000Z.
  Read copies are in .prismalens/runs/cmh3x9k2p0001/ in your working directory (read-only):
  - telemetry-prometheus-1.json  prom-prod (prometheus): 3 alerts firing in the window, 1 scrape targets down in the window
  - telemetry-loki-1.json  LOKI_URL (loki): 0 error log lines from 0 streams for {service_name="checkout"} (the default selector)
  - past-incidents.json  2 similar past incidents
  - runbooks.md  2 runbooks from the bound repos
  Read: prom-prod (prometheus): 3 alerts firing in the window, 1 scrape targets down in the window.
  Queried, nothing for the window: LOKI_URL (loki): 0 error log lines from 0 streams for {service_name="checkout"} (the default selector).
  Skipped before the run: am-prod (alertmanager): the source did not answer in time.
```

A follow-up on the run reads the same stored snapshot again; a new
investigation fetches a fresh one. When the snapshot could not be saved, the
run says so, and a follow-up on it starts with **No snapshot for this run**. A
repository that already tracks `.prismalens`, or has its own
`.prismalens/runs/.gitignore`, gets no copy; the snapshot is still stored and
in the prompt.

## During the run: PrismaLens's own tools

Every agent gets one MCP server from PrismaLens with four tools, all
read-only:

| Tool | What it returns | Cap |
| --- | --- | --- |
| `incident_get` | An incident PrismaLens recorded, by number, or the run's own: its title, status, severity and service, its alerts, and the deploy and change events for its services from a day before it started | |
| `investigations_search` | Past investigations matching `query`, optionally for one `service`, newest first. What the agent concluded and the cause an operator recorded stay in separate fields | `limit` 1 to 20; never the calling run |
| `runbooks_list` | The runbooks in the bound repositories, at the commit the run read | |
| `runbooks_read` | One runbook's markdown | 32,000 characters |

The server's name is `prismalens-` and ten random characters, new for each
run, so it never collides with a server in your own agent config. Its token
works for that run only: another run's token, a missing one and one from a run
that has ended all get `401`. The prompt tells the agent:

```text
PrismaLens tools (MCP server `prismalens-k3vq7x2mfa`, read-only): `incident_get`, `investigations_search`, `runbooks_list`, `runbooks_read`.
For metrics, logs and other live data, use the tools your own setup gives you.
```

deepagents gets the server as a config file for the run; every other agent gets
it over ACP. The tools line goes into the prompt only once the agent's first
request with the run's token arrives, within five seconds of the session
starting. **Run details → PrismaLens tools** shows whether they reached the
model: **Reached the model (first call 14:02:31)**, **Connected, not yet
called**, or **Did not reach the model**, with each turn's calls. Gemini CLI
loads MCP servers only in a folder its trust setting allows, and PrismaLens
does not change that setting; if you use folder trust, trust the runs folder
shown there.

## Your own tools and MCP servers

PrismaLens ships, installs and forwards no data-access tool. The MCP servers
your agent loads in your terminal load in the run too, from your own agent
setup; see [What a run inherits from your agent
setup](/coding-agents/#what-a-run-inherits-from-your-agent-setup). Whatever
the agent queries live, it queries with those, under your agent's own
permissions and the run's [permission
level](/coding-agents/#permission-levels-and-asks).

## Deploys

Deploys reach investigations as events you send, then through the incident's
context and `incident_get`. From the deploy job:

```bash
curl -X POST "$PRISMALENS_URL/api/webhooks/deploy" \
  -H "Authorization: Bearer $PRISMALENS_WEBHOOK_SECRET" \
  -H "Content-Type: application/json" \
  -d "{\"service\":\"web\",\"version\":\"$(git rev-parse HEAD)\",\"environment\":\"production\"}"
```

The `environment` field is what a connection's **Deployment tag** matches when
no alert label names a deployment.
[Record deploys](/guides/record-deploys/) has the rest of the fields.

## What stays out of the agent's reach

- **Source credentials stay in PrismaLens.** PrismaLens makes the requests
  itself. A saved credential is sent only to the origin of its connection's
  own address; a request or redirect to another host fails before anything is
  sent there.
- **The snapshot is scrubbed.** Every credential value, including the base64
  form of basic auth, is removed from the snapshot, the run log and the report
  before they are written. A credential shorter than 4 characters cannot be
  scrubbed, so that source is skipped.
- **PrismaLens's own variables are withheld.** The agent inherits your
  environment without any `PRISMALENS_*` variable and without
  `PROMETHEUS_TOKEN`, `ALERTMANAGER_TOKEN` and `LOKI_TOKEN`; see [The
  environment the agent gets](/coding-agents/#the-environment-the-agent-gets).
- **The tool token dies with the run.** It ends when the run ends, fails or is
  stopped, and a restart forgets every token.

What is not caught: an upstream that echoes a credential in a successful
answer, in an encoded form, reaches the snapshot. Prefer read-only tokens where
the service offers them.
