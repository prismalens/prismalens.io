An investigation is only as good as the code the agent reads. In PrismaLens a
**service** is the thing that alerts (an API, a worker, a database), and its
**Repository** field says where that service's code lives.

If a service has no repository, investigations still run, but in an empty
folder. The report says so at the top, and it cannot describe the code that
failed.

## Set the Repository field

Open **Services**, then **Add service** (or edit an existing one), and fill in
**Repository** with one of these:

| You type | PrismaLens treats it as |
| --- | --- |
| `/home/me/code/payments` or `~/code/payments` | A folder on this machine |
| `https://github.com/acme/payments.git` | A git URL over HTTPS |
| `git@github.com:acme/payments.git` or `ssh://git@host/acme/payments.git` | A git URL over SSH |

Relative paths and `file://` URLs are refused.

When you save, PrismaLens asks git about the source and shows the answer on
the service:

```text
main at 3f2c9a1b04de
```

If git cannot read it, you see git's own error, word for word, for example:

```text
fatal: repository 'https://github.com/acme/payments.git/' not found
```

The service still saves, so you can fix the problem and save again.

<Aside type="tip" title="Monorepos">
Point the field at the package folder, such as `~/code/platform/services/payments`.
PrismaLens finds the top of the repository, snapshots all of it, and starts the
agent in `services/payments`.
</Aside>

## What happens on every run

PrismaLens never runs the agent in your own checkout. Each investigation gets
its own copy:

- **A folder** is cloned with `git clone` into the run's directory. Git
  hardlinks the objects, so this takes about a second, needs no network and no
  token.
- **A URL** is kept as a bare mirror under `~/.prismalens/repos/`. Before each
  run PrismaLens fetches the mirror, then clones the default branch from it into
  the run's directory.

The copy lands in `~/.prismalens/runs/<investigation id>/repo`, and the agent
starts there. The incident timeline records which source and which commit the
run read.

<Aside type="caution" title="What a snapshot leaves out">
A snapshot is the last commit. Uncommitted changes, git submodules and Git LFS
file contents are not included. If you are debugging a change you have not
committed yet, commit it (a local branch is fine) before you run.
</Aside>

## Investigation notes

**Investigation notes**, in the service's form, holds what the agent should
know first about this service: dashboards, usual causes, what not to touch.
It takes up to 4096 characters. Every run on the service gets the notes in its
brief, fenced as runbook notes from you.

## Several services, several repositories

An incident can involve more than one service: its own, plus every service its
alerts name. Each run reads every repository those services link, not only the
first one.

- **One repository** keeps the layout above: `runs/<id>/repo`, with the agent
  starting in it (or in its monorepo folder).
- **Several repositories** each get a folder under `runs/<id>/repos/`, named
  after the repository, and the agent starts in `runs/<id>/repos` so it sees
  all of them. Two repositories with the same name get `api` and `api-2`.
- **One repository linked by two services** is cloned once.

A monorepo folder does not change where the agent starts in this layout; the
agent is told which folder belongs to which service. For an incident on
`checkout` whose alerts also name `jobs`, the incident timeline shows:

```text
Investigating the service's repositories
Investigating snapshots of 2 repositories: api (URL git@github.com:acme/api.git)
at main 1a2b3c4, worker (URL git@github.com:acme/worker.git/svc/jobs) at main
5d6e7f8. Uncommitted changes are not included.
```

and the agent is given:

```text
- Application SOURCE CODE: 2 repositories under your current working directory:
    api/  services: checkout  (at 1a2b3c4d5e6f)
    worker/  services: jobs  (at 5d6e7f8a9b0c)  sub-path: svc/jobs
```

Under WSL2, keep the repository on the Linux filesystem rather than under
`/mnt/c`. Cloning across the two filesystems copies every object on every run
and is slow.

## Dependencies

Record which services call which, so the agent knows what sits next to the one
that alerted.

Open **Services**, then a service, then **Dependencies**, and choose **Add**.
Pick a **Service** and a **Direction**:

- **Upstream:** this service calls the other one.
- **Downstream:** the other one calls this service.

The link also shows on the other service, with the direction reversed. Use
**Remove** on either side to delete it.

An investigation on the service is told both sets of neighbours, one hop out:
the services that call it and the services it calls.

Deleting a service removes its dependency links too. The confirmation lists
them, for example "Its 2 dependency links go too: book-metadata depends on it.
It depends on postgres."

## Private repositories

A clone uses this machine's own git login (your SSH keys, or the credential
helper your terminal's git uses) or a git host token you add under **Settings
→ Integrations**. Each repository in the service's **Code** section says which
one it clones with, for example `Code: machine git (gh, sumit)`, and when two
saved tokens match its host, a picker sets which one. See
[Git credentials](/guides/git-credentials/) for the order PrismaLens picks in
and what each failure says.

Git never prompts during a clone. A clone that would need a password fails
straight away with a message that says what to do instead of hanging.

PrismaLens needs `git` on the machine that runs `pl up`; `pl doctor` checks
for it.
