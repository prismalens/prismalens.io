When an investigation finishes, its report fills the incident's
[overview](/guides/overview/): the summary in Situation, the likely cause and
its evidence under **Why**, and its ways to stop the impact under **Stop the
impact**. Everything else is in the run's **Run details** panel. This page
explains each part and how to use it.

## Treat it as a lead

A report is a strong first theory from a colleague who read the code and ran
the commands. It is not a verdict. Models are not deterministic, so two runs on
the same incident can disagree, and a confident sentence can still be wrong.

The report is built so you can check it fast. Every claim points at the
command, file or log line behind it. If a run found nothing to stand on, the
root cause says so instead of inventing one.

## No confidence scores, on purpose

You will not see "87% likely" anywhere. A model has no calibrated way to tell
87 from 72, so a number like that looks precise and means nothing. PrismaLens
shows what a score would have summarised: the hypotheses in order, and the
evidence for and against each one.

## The parts of a report

**Summary.** Two or three sentences on what happened. It is the brief at the
top of the overview.

**Root Cause Analysis.** The specific code path, configuration, dependency or resource
the agent believes produced the alert, with a category: code, config,
infrastructure, external, or unknown. It can be empty. An empty root cause
means the agent could not tell, which is more useful than a guess.

**Culprit.** When the agent can name them: the service, the change (a commit
or deploy), and the mechanism. Any of the three can be blank. The change and
the mechanism show as facts beside the brief.

**Hypotheses.** Listed from most to least plausible. The order is the ranking.
The top one is the likely cause under Why, tagged **Confirmed**, **Likely**
or **Unconfirmed**; the rest are under **Also possible** in Run details. Each
one has a status and its evidence:

| Status | Meaning |
| --- | --- |
| `confirmed` | The evidence shows it directly. |
| `supported` | The evidence points this way but does not prove it. |
| `speculative` | Plausible, with no evidence yet. |
| `refuted` | Checked and contradicted. |

Each piece of evidence says whether it supports or contradicts the hypothesis
(**For** or **Against**), what was observed, where it came from (the command
that was run or the file that was read), and whether the agent verified it or
inferred it. Clicking a piece of evidence opens the step that found it.

**Ruled out.** Causes the agent considered and dropped, each with the reason
and the evidence. This tells you which paths are already walked.

**Coverage.** Two lists: what the agent queried, and what it did not, under
**Checked** and **Not checked** in Run details. Something on the second list
is not an all-clear, it was never looked at.

**Next steps.** What to do next, in rank order. Up to three ways to stop the
impact, each with a command where there is one, appear under **Stop the
impact**, where you copy one, mark it applied and check it (see
[Walking a fix](/guides/overview/#walking-a-fix)). The fix for the cause is
**Lasting fix** under Why. All of them are under **Agent's suggested next
steps** in Run details.

**Content tried to instruct the agent.** Shown only when it happened: text in
the alert or in command output that tried to give the agent orders, such as
"ignore previous instructions", quoted with where it was found. It is listed
first under **Flagged** in Run details, the details icon carries a red dot,
and a note beside any command under Stop the impact asks you to read it before
you run it.

**Run.** Run details → Summary names the coding agent and its version, the
model, the effort and the permission level the run used. When the agent
reports running a different model from the one asked for, the transcript's
model chip warns, for example **Sonnet, asked Opus**, and Summary says which
model ran. The export's `Run:` line says the same. What the agent could do
follows from its permission level (see
[Coding agents](/coding-agents/)).

**Facts PrismaLens supplied.** Before a run, PrismaLens gives the agent what it
already knows: changes in the alert's window, the services one hop away (both the
services that call the affected service and the services it calls), and
similar past incidents. Evidence the agent took from these without checking it
with a command is always marked **inferred**, never verified.

## Checking a hypothesis in two minutes

1. Read the top hypothesis and its status.
2. Click its first supporting piece of evidence to open the step, and run the same command, or open the same file, yourself.
3. Look at **Ruled out** before you chase the second hypothesis. The agent may already have been there.
4. If the report is wrong, open the run's transcript to see where the reasoning went off. Every tool call is recorded.

## Opening the evidence at its revision

</Aside>

A line like `src/pool.ts:88` is only worth something if it is the line the
agent read. The code moves on, so PrismaLens opens it at the commit the run
recorded.

1. Open the run's **Run details**, **Evidence** tab.
2. Click a citation of the form `src/pool.ts:88 @ 3f2c9a1`, or **Open the file
   at 3f2c9a1** on a step that read a file. The Why card's evidence opens the
   file directly.
3. A read-only, line-numbered view opens at the cited line, which is
   highlighted. On a phone it covers the screen, and Back returns you to the
   citation.

**Files the agent read** lists every file the run read, grouped as
`repo @ 3f2c9a1`, in the order it first read each, with `read x2` for a repeat.
New tool calls never move the file you have open.

The file comes from the repository the run cloned, or its mirror, read-only at
that commit. Only a tracked file at a commit this run recorded opens; anything
else is refused. Binary files and files over 1 MiB are named, not shown. A
symlink shows the path it points to.

When it cannot show the file, the view says why:

| State | Shown |
| --- | --- |
| `source-removed` | The source this run cloned is gone: the folder was removed, or the mirror was pruned. |
| `commit-gone` | Commit `abc1234` is no longer in the repository. |
| `not-retained` | Not committed at `abc1234`: the file was untracked or uncommitted when the run read it, and PrismaLens does not keep those. |
| `not-a-file` | At `abc1234` this path is a folder or a submodule, not a file. |

Pruning a mirror turns old citations into `source-removed`, so keep mirrors for
as long as you want to open old evidence.

## Sharing it

**More actions → Export report as Markdown**, in the incident's header,
downloads the newest report as `INC-<n>-report.md`. It names no agent or
model. To share a short update instead, **More actions → Write a status
update** drafts one from the incident (see
[The incident overview](/guides/overview/#the-header-and-the-latest-run-strip)).

## After you resolve it

**Resolve** asks what actually caused the incident, and a category. Both are
optional and start from the report. When a later incident looks similar, its
report lists this one under similar incidents with the cause you wrote, and
the next investigation is told about it as an inferred fact. What you write
at resolve outranks what the report guessed. The export carries it too, under
**Actual cause (recorded by a person)**. See
[Resolving and reopening incidents](/guides/incident-lifecycle/).

## When there is no report

A run that fails has no report. Why says what went wrong and shows the run's
last steps, and an older run's finding, if there is one, stands. PrismaLens
never fills in a report for a run that gathered no evidence.

A run you stopped has no report either. It reads **Stopped by you**, and
everything the agent found before you stopped it stays in its transcript.
To go on from where it stopped, see
[Stop, then continue](/guides/incident-lifecycle/#stop-then-continue).
