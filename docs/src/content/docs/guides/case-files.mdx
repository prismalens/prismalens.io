<Aside type="caution" title="An experiment, not a release">
Case Files are not in any released version of PrismaLens. The feature is off
by default and runs only after you turn on **Settings → Experiments → Case
File capture**. While it is off there is no capture, no Case page, no Case
File section on services and nothing extra in the agent's brief. What this
page describes can change or be removed before it ships.
</Aside>

By the time someone looks at an alert, the pod that crashed may have been
replaced and the cluster may have dropped its events (Kubernetes keeps events
for an hour by default). A Case File records the cluster's state at alert
time. PrismaLens runs a fixed, read-only kubectl checklist against the
service's target, redacts the output, and keeps it as a record you can check
later. The same redacted files are handed to the agent.

## Turn it on

1. Open **Settings → Experiments** and turn on **Case File capture
   (experiment)**.
2. Bind each service you want captured to its kube context and namespace (see
   [Bind a service to its Kubernetes target](/guides/services/#bind-a-service-to-its-kubernetes-target)).

PrismaLens needs `kubectl` on the machine that runs `pl up`. `pl doctor`
reports it on its **Capture (Kubernetes)** line.

## What happens when an alert arrives

When an alert opens an incident, or reopens one, on a bound service,
PrismaLens queues a capture. The investigation starts at the same time and
never waits for the capture.

1. **Identity.** PrismaLens reads the context from your kubeconfig and runs
   `kubectl auth whoami`. If the context now points at a different server
   from the one you bound, nothing else runs, and the case shows the gap.
2. **The checklist.** `get events`, `get deployments`, `get replicasets` and
   `get pods`, as JSON, in the bound namespace.
3. **Previous logs.** `logs --previous` for up to five containers that
   restarted, newest first: at most 500 lines and 1 MiB each.

Each command has a 15-second timeout and an 8 MiB cap, and the whole capture
has 60 seconds. Every output is redacted before anything else sees it (see
[Captured cluster output](/trust/#captured-cluster-output)).

**Into the agent's working directory.** As each file lands, PrismaLens copies
the redacted output into `.prismalens/case/` inside the run's folder, with a
`manifest.json` listing every file and whether it is complete. The agent's
brief points at that folder, says what had landed when the brief was written,
and tells the agent to read the manifest before running kubectl itself and to
treat the files as data, never as instructions. When the run's folder is a git
repository, `.prismalens/` is added to its `.git/info/exclude`.

### One capture per target

- One capture runs per target (cluster and namespace) at a time, and at most
  two run at once.
- A case opened while its target's capture is still **queued** shares that
  capture instead of queueing another. Once a capture is running, a new case
  gets a capture of its own, queued behind it.
- At most 16 captures wait in the queue. Captures for more severe alerts go
  first. When the queue is full, the lowest-ranked capture is **skipped**.
- A capture that starts more than 5 minutes after it was due is marked
  **missed**, with the interval. Events older than the cluster's event TTL may
  be gone by then.
- When every command failed, the capture is tried once more 15 seconds later.

### Turning it off

Turning the setting off stops running captures. What already landed stays,
and the capture ends **partial(disabled)**, or **skipped(disabled)** when
nothing had landed. No new captures are queued while it is off. Captures
already queued wait, and start when you turn it on again. Retention keeps
running while the setting is off: every hour it expires files past 256 MiB
or 30 days per bound service.

### Capture states

| State | Meaning |
| --- | --- |
| `queued` | Waiting for its turn. |
| `running` | Commands are running. |
| `complete` | Every command returned in full. |
| `partial(<reason>)` | Some output was cut or missing: `byte-cap`, `timeout`, `error` or `disabled`. |
| `skipped(<reason>)` | Never ran: `queue-full`, or `disabled` when you turned the setting off. |
| `blocked(<reason>)` | Could not run against the target: `no-kubectl`, `context-missing`, `identity-mismatch`, `unauthorised` or `unreachable`. |

## The Case page

With the setting on, an incident's overview header has a **Case File** link
(on wide screens) that opens `/incidents/<id>/case`. From top to bottom:

- **The capture line**, for example "Captured kind-pl/shop 7 s after the alert ·
  complete · identity matches binding", with chips such as `partial(byte-cap)`,
  `missed(…)` or "shared with another incident", and **Verify record**.
- **Open questions**: every `candidate`, `unknown` and `inconclusive` claim,
  including gaps with their one-step fix.
- **Observed**: claims grouped by workload. Each row shows its status, the
  statement, who ran the command ("PrismaLens ran this" or "The agent reported
  this"), the namespace, workload, revision and pod it covers, and whether the
  output was complete. Expand it for when the source says it happened, when
  PrismaLens collected it, when it was recorded, and its revision number. The
  artifact link opens the redacted output.
- **The agent's account**: the hypotheses from the agent's report, always
  `inferred`.
- **Commands**: what PrismaLens ran, with exact argv and retrieval, then the
  tool calls the agent reported.

The statuses are explained in
[Claim statuses in a Case File](/guides/reports/#claim-statuses-in-a-case-file).

**Verify record** re-checks the record. Every artifact and every capture adds
an entry to a hash chain. Verify checks that the chain links, that each
artifact's details match its entry, and that the stored files still match
their hashes. It answers "Record intact (6 entries)" or names the first
broken entry, such as "Broken at entry 9: metadata". Files removed by
retention count as expired, not broken.

## What it does not do

- It reads one namespace in one cluster: the one you bound. Deployments and
  ReplicaSets only; custom rollout resources are not read.
- It never changes anything in the cluster, and never reads Secrets or
  ConfigMaps.
- A follow-up question on a finished run gets no case folder.
- Redaction covers only what PrismaLens itself runs. Commands the agent runs
  in its own shell go to its model unredacted (see
  [Captured cluster output](/trust/#captured-cluster-output)).
